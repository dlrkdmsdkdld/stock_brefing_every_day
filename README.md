# 보유 주식 가격·뉴스 브리핑

매일 아침 보유 종목의 종가와 오늘자 뉴스를 모아 요약·판단까지 붙인 브리핑을 만듭니다.

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
./daily.sh          # 전체 파이프라인 (가격 -> 뉴스 -> 요약 -> 브리핑)
```

개별 실행:

```sh
.venv/bin/python prices.py   # 종가        -> prices.json
.venv/bin/python news.py     # 오늘자 뉴스  -> news.json
.venv/bin/python summarize.py # 요약·판단   -> verdicts.json
.venv/bin/python brief.py    # 브리핑       -> briefing.md, briefing.html
.venv/bin/python notify.py   # 텔레그램 전송
```

## 종목 추가·삭제 (`holdings.json`)

종목 목록은 `holdings.json` 한 곳에만 있습니다. 두 그룹으로 나뉩니다.

| 그룹 | 키 | 수집 범위 | 브리핑 위치 |
| --- | --- | --- | --- |
| 보유 종목 | `holdings` | 가격 + 지표 + **뉴스·요약·판단** | `보유 종목` 탭, 종목별 뉴스 |
| 관심 종목 | `watchlist` | 가격 + 지표만 | `관심 종목` 탭 |

보유 종목에 `"news": false`를 주면 **그 종목만 뉴스를 건너뜁니다.** (현재는 전 종목 켜져 있습니다.) 가격·등락률·RSI·볼린저·시총은
그대로 나오고 표에서 사라지지도 않습니다. 요약 토큰을 줄이면서도 종목을 목록에서 빼지 않으려고
둔 스위치이며, `true`로 바꾸거나 그 줄을 지우면 바로 다시 수집합니다.

```json
{"name": "마이크로소프트", "ticker": "MSFT", "currency": "USD",
 "keywords": ["Microsoft", "MSFT"], "query": "\"Microsoft\" stock", "news": false}
```

관심 종목은 평소 뉴스를 수집하지 않지만, **볼린저밴드 하단을 이탈하면** 그날은 뉴스를 찾아
`오늘의 특이점` 섹션에 함께 싣습니다. 급락에는 이유가 있을 가능성이 높기 때문입니다.
관심 종목은 한글 표시명만 있어 검색어로 못 쓰므로, `prices.json`에 남은 야후 상호에서
법인 접미어(Inc., Corporation 등)를 떼어 검색어를 만듭니다 (예: `McDonald's Corporation` → `"McDonald's"`).

관심 종목에는 `sector`를 붙여 브리핑에서 **섹터 탭**으로 나눠 봅니다
(AI·반도체 / AI 인프라·데이터센터 / 빅테크·소프트웨어 / 전력·에너지 / 산업·인프라 /
소재·자원 / 우주·방산·모빌리티 / 금융·핀테크 / 헬스케어·바이오 / 소비·배당).
종목이 90개라 한 표에 놓으면 훑기 어렵기 때문입니다. `전체` 탭에서 한꺼번에 볼 수도 있습니다.
새 종목에 `sector`를 안 적으면 `기타`로 묶입니다.

관심 종목은 시가총액도 함께 받아 **시총 내림차순**으로 정렬합니다. 시총은 야후가 주는
최신가 기준 값 대신 **상장주식수 x 우리가 쓰는 종가**로 계산해 표시 가격과 기준을 맞춥니다.
ETF처럼 시총 개념이 없는 종목은 `market_cap_error`로 남기고 목록 끝에 둡니다.

관심 종목은 그 외에는 뉴스를 수집하지 않습니다. 종목 수가 늘어도 요약 비용이 늘지 않고,
브리핑이 길어지지도 않습니다. 같은 티커가 양쪽에 있으면 보유 쪽만 남깁니다.

보유 종목에 한 줄 추가하면 가격·뉴스·브리핑이 모두 따라갑니다.

```json
{"name": "엔비디아", "ticker": "NVDA", "currency": "USD",
 "keywords": ["Nvidia", "NVDA"], "query": "\"Nvidia\" stock"}
```

- `currency`가 `KRW`면 국내(pykrx + NXT + 네이버 뉴스), 아니면 해외(Yahoo)로 처리합니다.
- `keywords`는 기사 제목에 이 말이 있으면 "직접 언급"으로 봅니다.
  영문 키워드는 대소문자를 지켜 단어 단위로 찾습니다. 소문자까지 허용하면
  `First Solar`가 `the first solar panel recycling program` 같은 무관한 제목에 걸립니다.
- `query`는 구글 뉴스 RSS 검색어입니다. 해외는 큰따옴표로 묶어야 정확도가 오릅니다.

관심 종목은 뉴스를 안 보므로 `keywords`·`query`가 필요 없습니다.

```json
{"name": "엔비디아", "ticker": "NVDA", "currency": "USD"}
```

## 가격 (`prices.py`)

국내는 pykrx(KRX)가 1차 출처이고, 같은 거래일의 Yahoo·네이버 종가와 교차 검증해
`match` / `mismatch` / `unavailable`을 기록합니다. 해외는 Yahoo 단일 출처입니다.
**아직 안 끝난 세션의 일봉만** 제외합니다. 장중 값을 종가로 오인하지 않는 것이 목적이지
마감된 종가를 버리는 것이 아니므로, 시장이 이미 닫혔으면 그날 일봉까지 씁니다
(마감 기준: KRX 15:40, 뉴욕 16:15 — 정규장 마감에 종가 확정 여유를 더한 값).

이게 실행 시각과 맞물립니다. 06:30 KST는 뉴욕 기준 전날 17:30이라 16:00에 끝난
그날 미국 종가가 확정돼 있고, 국내장은 아직 열리기 전이라 직전 거래일 종가가 최신입니다.
직전 거래일 대비 등락률(`change_pct`)도 함께 계산하며, 7일 초과 데이터는 `stale`로 표시합니다.

국내 종목에는 넥스트레이드(NXT) 최종 체결가를 `nxt_price` / `nxt_change_pct`로 덧붙입니다.
NXT는 애프터마켓이 20:00까지라 15:30에 끝나는 KRX 종가와 다릅니다
(9/4 삼성전자 KRX 255,500 / NXT 257,000). pykrx와 네이버 종목 API 모두 NXT를 제공하지 않아
네이버 금융 종목 페이지의 NXT 탭을 파싱하는데, 그 화면에는 거래일이 없습니다.
그래서 등락률로 역산한 전일 종가가 KRX 전일 종가와 0.2% 이내로 맞을 때만 표시하고
어긋나면 `nxt_error`로 남깁니다. 등락률·정렬·검증의 기준은 KRX 종가입니다.

pykrx 1.2.8은 임포트 시 `KRX 로그인 실패...` 메시지를 출력하지만 종목별 일별 시세
(`get_market_ohlcv_by_date`) 조회에는 계정이 필요 없습니다. `adjusted=False`(원주가)와
전종목 시세는 계정이 필요해 쓰지 않으며, 국내 종가는 수정주가 기준입니다.

## 기술적 지표 (`indicators.py`)

종가 시계열에서 두 가지를 계산해 `prices.json`과 브리핑에 넣습니다. 외부 라이브러리 없이
순수 함수로 두어 값을 검증하기 쉽게 했습니다.

- **RSI(14)** — 와일더 방식(대부분의 차트 프로그램과 동일). 70 이상 `과매수`, 30 이하 `과매도`.
- **볼린저밴드(20, 2σ)** — 이동평균 20일, 표준편차 2배. 표준편차는 모집단 기준(ddof=0)으로
  TradingView 등과 같은 방식입니다. 종가가 상단 밴드보다 높으면 `상단 이탈`,
  낮으면 `하단 이탈`, 아니면 `밴드 내`로 표시하고 `%B`도 같이 기록합니다.

지표는 종가와 **같은 데이터**로 계산합니다(국내는 KRX 수정주가, 해외는 Yahoo 미수정 종가).
안정적인 계산을 위해 시세를 150일치 받아 약 100거래일을 씁니다. 데이터가 모자라면
값을 지어내지 않고 `rsi_error` / `bb_error`로 남깁니다. 국내 지표는 KRX 종가 기준이라
NXT 가격과는 무관합니다. **참고용이며 투자 자문이 아닙니다.**

## 뉴스 (`news.py`)

**종목당 최대 1건**(`PER_HOLDING`)을 모읍니다. 출처는 국내가 네이버 금융 종목뉴스 + 구글 뉴스 RSS(ko),
해외가 Yahoo Finance + 구글 뉴스 RSS(en)입니다. 종목 단위로 병렬 처리하므로
종목이 늘어도 전체 소요 시간은 크게 늘지 않습니다(18종목 기준 약 6초).

날짜는 검색어가 아니라 제공처가 주는 발행 시각으로 확정합니다. 네이버는 `datetime`(KST),
Yahoo는 `pubDate`(UTC), 구글 RSS는 `pubDate`(GMT)를 KST로 변환해 비교하므로
미국 현지 기준 어제 저녁 기사도 한국시간 오늘이면 포함됩니다.

제목을 정규화해 유사도 0.72 이상이면 같은 기사로 묶고, 두 출처 이상에서 나타나면
`cross_confirmed`, 한 곳에서만 나오면 `single_source`로 표시합니다.
1건만 고르므로 **중요도 점수**로 정렬합니다. 종목이 제목에 직접 나오면 +4, 본문을 읽을 수 있으면 +3,
출처가 하나 늘 때마다 +2.5, 제목에 실적·목표주가·수주·인수·규제·급등락 같은 **주가에 영향을 주는 말**이
있으면 건당 +2입니다. 반대로 행사·캠페인·사회공헌·시상 같은 **홍보성 표현**은 건당 -4로 깎습니다.
1건만 뽑을 때 "대기질 개선 행사" 같은 기사가 올라오면 브리핑이 쓸모없어지기 때문입니다.
점수가 같으면 최신 기사를 앞에 둡니다.

## 본문 추출 (`article.py`)

고른 기사에는 실제 본문을 붙입니다. 잘 읽히는 순서대로 시도하고, 실패는 `body_error`로 남깁니다.

1. **네이버 뉴스 원문** — 국내 기사
2. **구글 링크 복원 후 원문** — 구글 RSS 링크는 `AU_yqL...` 형태의 암호화 리다이렉트라
   그냥은 못 엽니다. 기사 페이지에서 `data-n-a-id` / `data-n-a-ts` / `data-n-a-sg`를 읽어
   구글의 `batchexecute` 엔드포인트로 실제 매체 URL을 복원한 뒤 그 페이지에서 본문을 뽑습니다.
3. **Yahoo 기사 URL에서 직접 추출**
4. **Yahoo가 주는 요약문** — 위가 모두 막혔을 때

본문 영역은 `#dic_area`(네이버), `#article-view-content-div`(국내 언론사 CMS 표준),
`itemprop="articleBody"`, `.entry-content`, `<article>` 등을 순서대로 찾고,
없으면 문단 태그를 모으고, 그것도 안 되면 `og:description`을 씁니다.
태그 중첩을 세어 본문 영역만 정확히 잘라내며 최대 2,500자로 자릅니다.

2026-09-06 기준 49건 중 **46건 본문 확보**(네이버 7, 복원 원문 38, 메타 설명 1).
못 읽은 기사는 브리핑에 `제목만 확보`로 표시하고 요약·판단을 하지 않습니다.

## 요약·호재/악재 판단 (`summarize.py` -> `verdicts.json`)

키워드 감성분석은 오답이 많아 쓰지 않습니다. 기사 본문을 모델에 보내 요약과 판단을 받습니다.

제공처는 순서대로 시도합니다. 앞이 한도(429)에 걸리면 다음으로 넘어가고, 한 번 넘어가면
남은 묶음도 계속 그 제공처를 씁니다.

| 순서 | 제공처 | 키 | 비고 |
| --- | --- | --- | --- |
| 1 | OpenAI 계정 1 (`gpt-5.6-luna`) | `OPENAI_API_KEY` | Responses API + JSON 스키마 강제 |
| 2 | OpenAI 계정 2 | `OPENAI_API_KEY_2` | 선택 |
| 3 | OpenAI 계정 3 | `OPENAI_API_KEY_3` | 선택 |
| 4 | OpenAI 계정 4 | `OPENAI_API_KEY_4` | 선택 |
| 마지막 | 예비 (기본 Gemini) | `GEMINI_API_KEY` 또는 `FALLBACK_API_KEY` | OpenAI 호환 채팅 API |

OpenAI 키는 `OPENAI_API_KEY_5`, `_6`까지 번호를 이어 붙일 수 있습니다(워크플로에도 이미 연결돼 있습니다).
**설정된 것만** 번호 순서대로 씁니다. 같은 키를 두 번 넣으면 한도도 같이 쓰므로 중복은 걸러냅니다.

예비 제공처의 모델은 **자동으로 고릅니다.** 모델명을 고정하면 제공처가 그 모델을 내렸을 때
404가 납니다(실제로 `gemini-2.5-flash`가 신규 사용자에게 막혔습니다). 그래서 모델 목록을 받아
텍스트 생성용이 아닌 것(임베딩·이미지·음성 등)을 걸러낸 뒤 값싼 순서(`flash-lite` → `flash` → `mini`)로
고르고, 같은 계열에서는 최신 버전을 집습니다. `FALLBACK_MODEL`을 지정하면 그게 우선입니다.

예비 제공처는 OpenAI 호환 엔드포인트면 무엇이든 됩니다. `FALLBACK_BASE_URL`만 바꾸면
다른 곳으로 갈아탈 수 있습니다. `json_schema`를 거부하는
제공처를 위해 `json_object`로 물러서는 경로도 넣었습니다.

2026-09-06 실측: OpenAI 한도 소진 상태에서 자동 전환되어 45건을 `gemini-flash-lite-latest`로
1분 30초에 처리했습니다(입력 32,458 / 출력 8,433 토큰).

> GitHub Models는 2026년 7월 30일자로 폐지되어 쓸 수 없습니다.
에이전트 루프를 돌지 않고 API를 직접 호출하므로 비용과 실행 시간이 예측 가능합니다.
본문이 없는 기사는 아예 보내지 않습니다 — 제목만으로 호재·악재를 붙이지 않기 위해서입니다.

각 항목은 `summary`(내용 2~3문장 요약), `stance`(호재/약한 호재/중립/약한 악재/악재),
`impact`(그렇게 보는 이유), `caution`(근거의 한계·반대 시각)을 가집니다.
JSON 스키마를 강제(`strict`)해서 형식이 어긋난 응답을 받지 않습니다.
기사를 12건씩 나눠 호출하고, 한 묶음이 실패해도 나머지는 살려 `호출실패`에 기록합니다.
**투자 자문이 아닙니다.**

```sh
OPENAI_API_KEY=... .venv/bin/python summarize.py   # .env에 적어두면 자동으로 읽음
SUMMARY_MODEL=gpt-5.6-luna BATCH_SIZE=12 .venv/bin/python summarize.py
```

### 요청 한도 (중요)

무료(미결제) OpenAI 계정은 **하루 요청 50건 · 토큰 10만** 정도로 제한됩니다
(`x-ratelimit-limit-requests` / `-tokens` 헤더로 확인 가능). 하루 44건 요약에
토큰 4만 정도가 필요하므로 **무료 계정으로는 며칠 안에 소진됩니다.**
결제 수단을 등록하면(최소 $5) 한도가 크게 올라가고, 실제 비용은 아래처럼 매우 작습니다.

### 미리 확인하기

`summarize.py --dry-run`은 호출하지 않고 필요한 토큰과 각 제공처의 남은 한도만 보여줍니다.

실제 호출 전에도 제공처마다 잔여 한도를 먼저 확인합니다. 남은 토큰이 그 묶음에 필요한 양보다
적으면 **시도하지 않고 바로 다음 키로 넘어갑니다.** 한도까지 다 태우고 실패한 뒤 넘어가면
쓴 토큰만 버리게 되기 때문입니다. 잔여 한도는 응답 헤더(`x-ratelimit-remaining-*`)에서 읽고,
헤더를 주지 않는 제공처는 "알 수 없음"으로 두고 일단 시도합니다.

## 매일 자동 실행 (GitHub Actions)

`.github/workflows/daily-brief.yml`이 **미국 정규장 마감 직후**에 실행됩니다. 한국시간으로 서머타임 때 **05:20**,
겨울에는 **06:20**입니다. 내 컴퓨터가 꺼져 있어도 돌아갑니다.

미국장 마감(16:00 ET)은 한국시간으로 계절에 따라 05:00과 06:00 사이를 오가는데
cron은 UTC 고정이라 하나로 맞출 수 없습니다. 그래서 **두 번 걸어 두고**
`check` 잡이 조건을 확인해 **하루 한 번만** 통과시킵니다.

| cron (UTC) | 한국시간 | 서머타임 | 겨울 |
| --- | --- | --- | --- |
| `20 20 * * *` | 05:20 | 실행 (뉴욕 16:20, 마감 후) | 건너뜀 (뉴욕 15:20, 장중) |
| `20 21 * * *` | 06:20 | 건너뜀 (이미 실행함) | 실행 (뉴욕 16:20, 마감 후) |

통과 조건은 두 가지입니다. **뉴욕 현지 16:15를 넘겼고**(마감 16:00 + 종가 확정 여유),
**오늘 아직 안 돌았을 것**(`prices.json`의 `fetched_at` 날짜로 판단). 수동 실행은 조건 없이 통과합니다.
앞 실행이 중간에 실패하면 `prices.json`이 갱신되지 않으므로 뒤 실행이 자동으로 재시도합니다.

GitHub의 예약 실행은 혼잡할 때 늦어집니다. 실측으로 06:30 예약이 08:03에 시작된 적이 있어
`:00`, `:30` 같은 혼잡 시각은 피했습니다. **지연은 GitHub 쪽 사정이라 없앨 수 없습니다.**
GitHub의 예약 실행은 혼잡할 때 수십 분 늦어질 수 있습니다.

가격 -> 뉴스 -> 요약 -> 브리핑 -> 텔레그램 전송 순으로 돌고, 결과(`briefing.md`, `briefing.html`,
`prices.json`, `news.json`, `verdicts.json`)를 저장소에 커밋하며 실행 아티팩트로도 첨부합니다.
각 단계는 `continue-on-error`라 한 단계가 실패해도 나머지는 진행합니다.

### 최초 설정

1. platform.openai.com에서 API 키를 발급합니다.

2. 저장소 → Settings → Secrets and variables → Actions → New repository secret

   | 이름 | 용도 |
   | --- | --- |
   | `OPENAI_API_KEY` | 기사 요약·판단 |
   | `TELEGRAM_BOT_TOKEN` | 브리핑 발송 |
   | `TELEGRAM_CHAT_ID` | 받는 사람 |

   `OPENAI_API_KEY`가 없으면 요약 단계만 건너뛰고 가격·뉴스·브리핑·발송은 정상 동작합니다.
   이때 브리핑의 각 기사에는 요약 대신 `판단 보류`가 표시됩니다.

3. Actions 탭에서 `데일리 브리핑` → `Run workflow`로 수동 실행해 한 번 확인하세요.

시각을 바꾸려면 워크플로의 `cron` 두 줄을 함께 고치면 됩니다 (UTC 기준, KST = UTC+9).

로컬에서 같은 파이프라인을 직접 돌리려면 `./daily.sh`를 쓰면 되고,
실행 기록은 `logs/날짜.log`에 남습니다.

## 텔레그램 전송 (`notify.py`)

브리핑 전문을 텔레그램으로 보냅니다. 가격·지표 표와 종목별 뉴스 요약·판단을 모두 담고,
텔레그램의 4096자 제한에 맞춰 줄 단위로 나눠 여러 건으로 보낸 뒤 `briefing.html`을 파일로 첨부합니다.

첫 메시지 맨 위에는 **브리핑 웹페이지 링크**가 붙습니다. 텔레그램 텍스트로는 표가 읽기 불편해서,
접기/펼치기가 되는 웹페이지를 바로 열 수 있게 한 것입니다. 주소는 `BRIEF_URL` 환경변수로 지정하고
(워크플로에서는 저장소 변수), 없으면 `GITHUB_REPOSITORY`로 Pages 주소를 유추합니다.

카카오톡은 개인 계정으로는 **'나에게 보내기'** 밖에 안 됩니다. 친구에게 보내기와 카카오톡 채널
메시지는 사업자등록과 앱 심사가 필요합니다. 그래서 텔레그램을 씁니다.

### 최초 설정

1. 텔레그램에서 `@BotFather`에게 `/newbot` → 봇 토큰을 받습니다.
2. 만든 봇과 대화를 시작해 아무 메시지나 한 번 보냅니다(봇은 먼저 말을 걸 수 없습니다).
3. chat id 확인:

   ```sh
   TELEGRAM_BOT_TOKEN=봇토큰 .venv/bin/python notify.py --whoami
   ```

4. GitHub 저장소 시크릿에 `TELEGRAM_BOT_TOKEN`과 `TELEGRAM_CHAT_ID`를 등록합니다.
   시크릿이 없으면 전송 단계만 건너뜁니다.

로컬 테스트:

```sh
TELEGRAM_BOT_TOKEN=... TELEGRAM_CHAT_ID=... .venv/bin/python notify.py
```

두 단계로 나눠 토큰을 아낍니다.

1. **데이터로 후보 좁히기** (토큰 0)

     점수로 합산해 상위 5개. 뉴스 화제성은 오늘 잡힌 기사 수인데 국내는 네이버·구글을 함께 훑어
     기사가 원래 많으므로, 절대 건수 대신 **같은 시장 안에서의 상대 순위**로 환산합니다.

     급등주만 올라오지 않도록 급락·거래활발 화면을 함께 봅니다.
2. **두 후보군을 한 번의 요청으로 전달** — 기사 본문은 보내지 않고 요약만 씁니다.

모델이 후보 밖 종목을 고르면 그 항목은 버립니다. 목록 밖 종목은 뉴스를 수집하지 않으므로
지표만으로 판단하며, 그 한계를 유의점에 적도록 지시합니다.
**매수·매도 권유가 아니라 "오늘 살펴볼 이유"를 정리하는 용도입니다.**

## 지난 추천 성적 (`track.py` -> `history.json`)

추천이 실제로 쓸모 있었는지 남깁니다. **모델을 쓰지 않아 토큰이 들지 않습니다.**
`recommend.py`가 고른 종목을 `history.json`에 쌓고, 매일 현재가를 받아 추천 시점 대비
수익률을 갱신합니다. 브리핑에는 최근 7건과 적중률·평균 수익률이 나옵니다.
30일이 지난 기록은 정리하며, 당일 추천은 아직 결과가 없으므로 성적에서 제외합니다.

표본이 적을 때 적중률은 의미가 약하므로 건수를 함께 보여주고 참고용임을 밝힙니다.

## 환율과 원화 환산

`prices.py`가 원/달러 환율(Yahoo `KRW=X`)을 함께 받아 `prices.json`의 `fx`에 넣습니다.
브리핑 머리말에 환율과 등락이 나오고, 보유 해외 종목 표에는 종가 아래 원화 환산액이 붙습니다.

한눈에 보기에는 **원화 기준 등락**을 따로 적습니다. 달러 기준으로 오른 날도 환율이 내리면
원화로는 덜 오르거나 손실일 수 있어서입니다. 계산은 `(1+주가등락)(1+환율등락)-1`입니다.
주말·휴일에는 마지막 고시 환율이 그대로 남으므로 기준 날짜를 함께 표시합니다.

## SEC 공시 감시 (`sec.py` · 별도 워크플로)

미국 공시를 **30분마다** 확인해 새로 올라온 것만 텔레그램으로 보냅니다.
모델을 쓰지 않으므로 **토큰이 들지 않습니다.**

| 서식 | 내용 | 제출 기한 | 대상 |
| --- | --- | --- | --- |
| **Form 4** | 임원·대주주 매매 | 거래 후 **2영업일** | 내 보유·관심 종목 |
| **8-K** | 실적·인수·경영진 교체·소송 | **4영업일** | 내 보유·관심 종목 |
| **13F-HR** | 기관 분기 보유 내역 | 분기말 후 **45일** | `filings.json`의 기관 |

Form 4는 본문 XML을 파싱해 **누가·어떤 직책으로·얼마나** 사고팔았는지까지 보여줍니다
(예: `Kurtz George · PRESIDENT AND CEO · 처분 $4.2M`).
13F는 전분기 정보표와 비교해 **신규 매수·청산 종목**을 함께 싣습니다.

> **13F는 이미 지난 정보입니다.** 분기말 기준을 45일 뒤에 내므로 발표 시점엔 그 기관이
> 이미 정리했을 수도 있습니다. 그래도 발표 당일 시장이 반응하므로 따라갑니다.

티커→CIK 변환은 SEC가 주는 `company_tickers.json`을 씁니다(해외 105종목 전부 매핑).
국내 종목은 SEC 대상이 아닙니다. SEC는 연락처가 든 User-Agent를 요구하므로
저장소 변수 `SEC_USER_AGENT`로 넘기고, 초당 요청도 벌려 둡니다.

이미 보낸 공시는 `seen.json`에 남겨 두 번 보내지 않습니다. **접수일이 아니라 확인한 날짜로**
보관하는데, 접수일 기준으로 정리하면 지난 분기 13F가 바로 지워져 매번 다시 알림이 나가기 때문입니다.

## 브리핑 (`brief.py`)

`prices.json` + `news.json` + `verdicts.json`을 합쳐 `briefing.md`와 `briefing.html`을 만듭니다.
상승/하락 종목 수와 평균 등락률, `보유 종목`/`관심 종목` 탭으로 나뉜 시세 표,
종목별 뉴스와 요약·판단, 데이터 신뢰도 주석을 한 문서에 담습니다.
보유 종목 표는 국내(NXT 병기)와 해외로 나뉘고, 관심 종목 표는 종가·변동액·변동률·RSI·볼린저만 보여줍니다.
등락 막대의 눈금은 보유·관심을 합친 최대 등락폭으로 잡아 두 탭이 같은 기준으로 보입니다.
오늘자 데이터가 없으면 `prices.py`·`news.py`를 먼저 실행하므로 이것만 돌려도 됩니다.
